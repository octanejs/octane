When someone changes the quantity in a shopping cart, the total should
change too. You can use `signal$` for the quantity, which you set directly,
and `derived$` for the total, which you calculate from the quantity. If a
value comes from a request, like a profile you look up by user ID,
`query$` lets you work with the result in much the same way. All three give
you a handle you can read by calling `.get()`.

If your app needs to decide how long to keep the data, you can use
[an explicit scope and resource](#explicit-resources). For records that
belong to the server, such as a list that several components read and edit
optimistically, see [Data](/docs/data).
[Best practices](/docs/best-practices#choose-where-state-lives) walks through
when to use component state, Signals, or Data. If you're looking for a
particular export, jump to the [application API reference](#reference).

**Each module that reads a signal during rendering needs its own runtime
import** from `octane/signals`, `octane/signals/client`, or
`octane/signals/server`. This includes a component that gets the handle
through props or calls a helper that reads it. The compiler needs that
runtime import even if the handle's name ends in `$` or you've imported its
type. If your module uses none of the named exports, add `import 'octane/signals';`.

<h2 id="declarations">Write state and derive a value</h2>

Here's the cart calculation in a browser module compiled by Octane. The
quantity is writable and the total is read-only. Each item costs 12, so
when you set the quantity to 3, you can read 36 from the total on the very
next line.

```ts
import { derived$, signal$ } from 'octane/signals';

export const quantity$ = signal$(1);
export const total$ = derived$(() => quantity$.get() * 12);

quantity$.set(3);
console.log(total$.get()); // 36, immediately.
```

Where you put these declarations determines who shares the cart. At module
level, components in the same browser document share the values. On the
server, each request gets its own copy. If you want a separate cart for each
mounted instance of a component, declare `signal$`, `derived$`, or `query$`
inside the component. You can use `derived$` there to calculate `total$`
just as you did at module level.

<h3 id="local-state">Keep state in a component</h3>

The `useSignal$` hook gives a component a writable signal of its own. This
counter subscribes to the count by calling `.get()` as it renders the button.
When the click handler calls `.set()`, the button shows the new count.

```tsrx
import { useSignal$ } from 'octane/signals/client';

export function Counter() @{
	const count$ = useSignal$(0);
	<button onClick={() => count$.set((count) => count + 1)}>{String(count$.get())}</button>
}
```

You can also pass a lazy initializer such as `useSignal$(() => 0)`. Octane
calls the function once, when it initializes that hook slot.

The `$` suffix tells you which names carry a handle. Keep it on the variable
and on any prop you pass the handle through. Once you've read the value, give
it an ordinary name, as in `const count = count$.get()`.

<h3 id="hooks-and-memos">Use signals with existing hooks</h3>

You can read the count inside a `useMemo` callback, too. When you leave out
the dependency array, the memo tracks the signals its callback reads. That's
enough to keep the label on this button up to date.

```tsrx
import { useMemo } from 'octane';
import { useSignal$ } from 'octane/signals/client';

export function Counter() @{
	const count$ = useSignal$(0);
	const label = useMemo(() => `Count: ${count$.get()}`);
	<button onClick={() => count$.set((count) => count + 1)}>{label}</button>
}
```

If you write the dependency array yourself, read the count during rendering
and put its current value in the array. That same value can go in an effect's
dependencies, too. Here the effect reports the count to the caller each time
it changes.

```tsrx
import { useEffect, useMemo } from 'octane';
import { useSignal$ } from 'octane/signals/client';

export function CountLog(props: { recordCount: (count: number) => void }) @{
	const count$ = useSignal$(0);
	const count = count$.get();
	const label = useMemo(() => `Count: ${count}`, [count]);
	useEffect(() => props.recordCount(count), [count, props.recordCount]);

	<button onClick={() => count$.set((n) => n + 1)}>{label}</button>
}
```

<h2 id="async-resources">Load data with query$</h2>

For a request that belongs to a component or module, `query$(select, load)`
lets you describe how to choose a key and how to load its data. In the
profile lookup below, the first function reads the selected user ID. The
second receives that ID and a context with an `AbortSignal` to pass to
`fetch`.

These examples run in the browser, where `/api` points to the app's own
origin. When rendering on the server, use a URL based on the incoming
request, or call a server function as in the
[streaming example](#streaming-example).

```ts
// user-data.ts — compile this module with Octane.
import { query$, signal$, skip } from 'octane/signals';

export type User = { id: number; name: string; revision: number };
export const selectedId$ = signal$<number | null>(1);
export const user$ = query$<number, User>(
	() => selectedId$.get() ?? skip,
	async (id, { signal }) => {
		const response = await fetch(`/api/users/${id}`, { signal });
		if (!response.ok) throw new Error(`User request failed: ${response.status}`);
		return response.json() as Promise<User>;
	},
);
```

Calling `selectedId$.set(2)` selects user 2. If you set the ID to `null`,
the selector returns `skip` and the query stays idle. The card checks for
that state before calling `.get()` so it can ask you to choose a user.
Once there's a selection, reading inside `@try` lets the card show a
loading message while it waits, the name when it arrives, or an error
if the request fails.

```tsrx
import 'octane/signals';
import { user$ } from './user-data';

export function UserCard() @{
	<section>
		@if (user$.snapshot().status === 'idle') {
			<p>Choose a user.</p>
		} @else {
			@try {
				<p>{user$.get().name as string}</p>
			} @pending {
				<p>Loading user…</p>
			} @catch (error) {
				<p role="alert">{String(error)}</p>
			}
		}
	</section>
}
```

If the card already has a name to show, `user$.refetch()` keeps that name
visible while it refreshes the current user. With `user$.reset()`, the card
can show its loading message again during the new attempt.

The ID can also come from a prop. This profile asks `loadUser` for the
display name that goes with the current ID. If the request fails, the retry
button resets the query to try the load again and resets the error boundary
so the profile can render the result.

```tsrx
import { query$ } from 'octane/signals';

function RetryButton(props: { retry: () => void }) @{
	<button onClick={() => props.retry()}>Retry</button>
}

export function Profile(props: {
	id: number;
	loadUser: (id: number, context: { signal: AbortSignal }) => Promise<string>;
}) @{
	const user$ = query$(() => props.id, props.loadUser);
	@try {
		<output>{user$.get() as string}</output>
	} @pending {
		<span>Loading</span>
	} @catch (_error, reset) {
		<RetryButton
			retry={() => {
				user$.reset();
				reset();
			}}
		/>
	}
}
```

<h3 id="streams">Consume streams</h3>

Your loader can also return an async iterable. Here the app's
`watchNotifications(id, signal)` returns an `AsyncIterable<Notification>`.
Pass `{ kind: 'stream' }` to `query$` so it reads the notifications as they
arrive.

```ts
import { query$, skip } from 'octane/signals';
import { selectedId$ } from './user-data';
import { watchNotifications } from './api';

type Notification = { text: string };
export const notification$ = query$<number, Notification>(
	() => selectedId$.get() ?? skip,
	(id, { signal }) => watchNotifications(id, signal),
	{ kind: 'stream' },
);
```

The query stays pending until the stream yields its first notification. Each
yield replaces the entire value, so reading the query gives you the most
recent notification. When the stream finishes, you can still read that last
value. If it finishes before yielding anything, the query reports an error.

<h2 id="shared-state">Own shared state with a scope</h2>

The cart from the first example might stay open as someone moves from one
screen to another. Its components come and go, and **your app decides how
long to keep the cart**. Create a scope once, when the cart opens, and pass
its handles to those components through props or context. When the cart
closes, dispose of the scope.

```ts
import { createScope } from 'octane/signals';

const cart = createScope({ scopeKey: 'cart' });
const quantity$ = cart.signal$('quantity', 1);
const unitPrice$ = cart.signal$('unit-price', 12);
const total$ = cart.derived$('total', () => quantity$.get() * unitPrice$.get());

quantity$.set(3);
console.log(total$.get()); // 36

const stop = total$.subscribe(() => console.log(total$.get()));
quantity$.set(4); // Notifies with 48; subscribe itself does not notify.
stop();

// When the cart's owning session ends:
cart.dispose();
```

Each key names a signal within this cart. A calculation made with
`scope.derived$` is synchronous, so you can read the new total as soon as
you set the quantity. To hear about later changes, call `subscribe`. It
returns a function you can call when you want to stop listening.

<h3 id="effects">Run an effect when values change</h3>

Suppose you want the browser tab's title to show how many items are in the
cart. With `scope.effect(run)`, Octane calls `run` right away and tracks
which signals it reads. After a batch that changes any of them, Octane runs
the effect again. Here the effect reads the label and copies it to the title.

```ts
import { createScope } from 'octane/signals';

const cart = createScope({ scopeKey: 'cart' });
const quantity$ = cart.signal$('quantity', 1);
const label$ = cart.derived$(null, () => `${quantity$.get()} items`);

const stop = cart.effect(() => {
	document.title = label$.get();
	return () => {
		document.title = '';
	};
});
```

The effect returns a cleanup function that clears the title. Octane calls
it before running the effect again and when the effect stops. The effect
keeps running until you call the `stop` function returned by `cart.effect`
or dispose of the cart.

The label is something the client can work out for itself, so `label$` has
a `null` key. You can leave a signal or calculation keyless this way if it's
only for use on the client. Give it a key if you need to serialize, seed,
or inspect it, or stage its value in a transition.

<h3 id="equality-and-watched">Control when a signal changes or starts</h3>

A write uses `Object.is` to check whether the value changed. For a chat
room, you might consider two lists of messages equivalent if they have the
same IDs in the same order. You can supply that check as `equals` in the
third argument to `scope.signal$` or `scope.derived$`. When it returns
true, the signal keeps the previous value, so Octane skips the calculations
and notifications that would follow a change. Keep `equals` free of writes
to signals.

The chat room also needs a connection while someone is reading its messages.
With `watched`, the first observer starts the connection. An effect, a
subscription, or a binding in the rendered UI can all observe the messages,
even through a derived value. Calling `.get()` on its own leaves the
connection closed if there are no observers. When the last observer leaves
or the scope is disposed, Octane calls the cleanup that `watched` returned.

Here the app's `chat.subscribe` gives you a function to unsubscribe. The
helper takes care of the case where you leave the room while the
connection is still opening.

```ts
import { createScope, ScopeDisposedError } from 'octane/signals';
import { chat, type Message } from './chat';

function subscribeSafely<T>(
	start: (publish: (value: T) => void) => (() => void) | Promise<() => void>,
	publish: (value: T) => void,
) {
	let active = true;
	let cleanup: (() => void) | undefined;
	const fail = (error: unknown) => {
		active = false;
		if (typeof reportError === 'function') reportError(error);
		else console.error(error);
	};
	let setup: (() => void) | Promise<() => void>;
	try {
		setup = start((value) => {
			if (active) publish(value);
		});
	} catch (error) {
		active = false;
		if (error instanceof ScopeDisposedError) throw error;
		fail(error);
		return () => {};
	}
	if (typeof setup === 'function') cleanup = setup;
	else
		void setup
			.then((stop) => {
				if (active) cleanup = stop;
				else stop();
			})
			.catch(fail);
	return () => {
		active = false;
		cleanup?.();
	};
}

const room = createScope({ scopeKey: 'room' });
const roomId$ = room.signal$('room-id', 'general');
const messages$ = room.signal$<Message[]>('messages', [], {
	equals: (previous, next) =>
		previous.length === next.length && previous.every((message, i) => message.id === next[i].id),
	watched: () =>
		room.effect(() =>
			subscribeSafely<Message[]>(
				(publish) => chat.subscribe(roomId$.get(), publish),
				(messages) => messages$.set(messages),
			),
		),
});
```

Returning the effect's stop function from `watched` keeps the subscription
open for as long as the messages have observers. The effect reads
`roomId$`, so switching rooms closes the old subscription and opens one
for the new room.

The `active` flag lets the helper ignore messages that arrive after you've
left. If the old connection finishes opening later, the helper immediately
calls the cleanup function it gets back. It reports errors from setup and
from this late cleanup through `reportError`, falling back to
`console.error` when needed.

<h3 id="transactions">Group writes you can undo</h3>

An editor might change a title and its tags in the same edit. With
`scope.batch(fn)`, observers hear about the changes together when `fn`
finishes. If `fn` throws partway through, the writes it made still stand.

For an edit that should succeed or fail as a whole, `scope.transaction(fn)`
groups the writes in a batch. If `fn` throws, Octane restores the previous
values before notifying any observers and rethrows the error. Returning a
promise also causes the transaction to roll back and throw. On success you
get `{ value, changes, undo, redo }`, so the editor can undo the title and
tags together.

```ts
import { createScope } from 'octane/signals';

const editor = createScope({ scopeKey: 'editor' });
const title$ = editor.signal$('title', '');
const tags$ = editor.signal$<string[]>('tags', []);

const edit = editor.transaction(() => {
	title$.set('Release notes');
	tags$.set(['docs']);
	if (title$.get().length > 80) throw new Error('Title is too long');
});

edit.undo(); // Restores both signals in one batch.
edit.redo();
```

You can inspect the edit with `changes`. It lists each changed signal once
as `{ signal$, previous, next }`, even if you wrote to it several times.
A nested transaction joins the outer edit. If the inner transaction fails,
its rollback covers just the writes it made.

<h3 id="explicit-resources">Load data in an explicit scope</h3>

In the earlier user lookup, `query$` handled selection and loading in one
declaration. If you already have a scope for the account, you can define
a reusable request and let each account choose which user to load.

- `query('user', load)` defines the request and returns a function. Call
  that function with an ID to describe which user to fetch.
- `createResource(account, 'selected-user', describe)` runs your selection
  callback and starts the load in the account scope. It gives you a handle
  you can read to get the result.

```ts
import { createResource, createScope, query } from 'octane/signals';

const fetchUser = query('user', async (id: number, { signal }) => {
	const response = await fetch(`/api/users/${id}`, { signal });
	if (!response.ok) throw new Error(`User request failed: ${response.status}`);
	return response.json() as Promise<{ id: number; name: string }>;
});

export function openAccount$(initialId: number) {
	const account = createScope({ scopeKey: 'account' });
	const userId$ = account.signal$('user-id', initialId);
	const user$ = createResource(account, 'selected-user', () => fetchUser(userId$.get()));

	return {
		user$,
		selectUser: (id: number) => userId$.set(id),
		refresh: () => user$.retry(),
		reload: () => user$.retry({ pending: true }),
		close: () => account.dispose(),
	};
}
```

With the account open, `selectUser(2)` loads another user. Once that user
is on screen, `refresh()` keeps their details visible while the request runs
again. Call `reload()` if you'd like to show the pending UI during the retry.
If two resources in the account scope select the same request, they share
the load. Call `close()` when the account session ends.

<h3 id="families">Keep one signal per key</h3>

On a task board, you might want a signal for each row, and the rows can
change as people add and finish tasks. A family lets you look up the
signal by task ID without reserving a scope key for every task. With
`createFamily`, the first lookup creates a keyless member in the scope.
Ask for the same ID again and you get that member back.

```ts
import { createFamily, createScope } from 'octane/signals';

const board = createScope({ scopeKey: 'board' });
const done = createFamily(board, (_id: string) => board.signal$(null, false), { idle: 30_000 });

done.get('task-1').set(true);
console.log(done.get('task-1').get()); // true

// When the task is deleted:
done.delete('task-1');
```

When a task leaves the board, `delete` evicts its member. The `idle`
option also evicts a member after it goes that many milliseconds without
an observer, which here means 30 seconds. Reading the old handle after
eviction throws. A later `get` for the same ID creates a fresh member.

By default, a family lasts only in memory. Its members are keyless, so
serializing the scope leaves them out of the seed. If you render the board
on the server and want to carry particular rows over to the client, save
their string keys and values together in one keyed signal reserved for the
family's namespace. Do this before serializing the request scope. On the
client, use that snapshot to initialize the selected members and let the
others start with their usual client defaults.

Even if a member is evicted, its last captured value stays in the snapshot
until you replace or clear it. The whole family still uses just one keyed
signal. The [tested family hydration recipe](https://github.com/octanejs/octane/blob/main/docs/signals.md#opt-in-to-family-hydration)
shows the full setup, including how to reserve a namespace for each family.

<h3 id="react-components">Read a scope from React</h3>

You can show the cart total in React using the same handles, without the
Octane compiler. The `useSignalValue(handle$)` hook from `octane/signals/react`
reads the total and re-renders the component when it changes. The button
can write through the quantity handle as usual. To give components further
down the tree access to the scope itself, wrap them in
`SignalScopeProvider`. They can then call `useSignalScope()` to get the cart.

```tsx
import { createRoot } from 'react-dom/client';
import { createScope } from 'octane/signals';
import { SignalScopeProvider, useSignalValue } from 'octane/signals/react';

const cart = createScope({ scopeKey: 'cart' });
const quantity$ = cart.signal$('quantity', 1);
const total$ = cart.derived$('total', () => quantity$.get() * 12);

function Total() {
	return <output>{useSignalValue(total$)}</output>;
}

createRoot(document.getElementById('root')!).render(
	<SignalScopeProvider scope={cart}>
		<Total />
		<button onClick={() => quantity$.set((n) => n + 1)}>Add</button>
	</SignalScopeProvider>,
);
```

The provider borrows the scope, so your app is responsible for its lifetime.
Create one per root or server request, and unmount the tree that reads it
before disposing of the scope. If you retire the scope while a component is
still reading it, the read throws `ScopeDisposedError` and React passes it
to the nearest error boundary.

Reading a pending async handle suspends the component, and reading a failed
one throws its error. If you're hydrating a server-rendered tree, create
the client scope with `seed: serverScope.serialize()`.

<h2 id="async-derived">Derive values across await</h2>

A `derived$` calculation can return a promise. Say you want to greet the
selected user in their language. The greeting depends on both the user and
the locale, and you might still be waiting for the user when the calculation
starts. Inside the async function, `await read(handle$)` tells Octane about
each dependency as you reach it, even after an earlier `await`. If the user
or locale changes, Octane cancels the old attempt and starts a new one.

```ts
import { derived$, signal$ } from 'octane/signals';
import { user$ } from './user-data';

export const locale$ = signal$('en');
export const greeting$ = derived$(async ({ read, signal }) => {
	const user = await read(user$);
	const locale = await read(locale$); // Tracked even after the first await.
	const response = await fetch(`/api/greeting/${user.id}?locale=${encodeURIComponent(locale)}`, {
		signal,
	});
	if (!response.ok) throw new Error(`Greeting request failed: ${response.status}`);
	return response.text();
});
```

<h3 id="availability">Choose what to show while waiting</h3>

So far the profile has read the user with `.get()` and relied on a boundary
to handle loading and errors. You might prefer to keep the previous profile
on screen while the next one loads. With `.latest(fallback)`, you get the
last successful result, even if the next attempt is pending or has failed.
You'll get the fallback until the first result is ready. When you need to
tell idle, pending, ready, and error states apart, read `.snapshot()`. It
also tells you whether a refresh is underway.

```tsrx
import { derived$ } from 'octane/signals';
import { user$ } from './user-data';

const card$ = derived$(() => ({
	id: user$.get().id,
	name: user$.get().name,
}));
export function UserSummary() @{
	const card = card$.latest(null);
	@if (card) {
		<p>
			{String(card.id)} · {card.name as string}
		</p>
	} @else {
		<p>No user loaded yet.</p>
	}
}
```

The card derives the ID and name together. Reading `card$.latest(null)`
during rendering keeps both fields from the same user on screen until the
next user's card is ready.

<h2 id="optimistic-actions">Save with optimistic feedback</h2>

When someone edits their name, you can show the new name right away with
`optimistic$` while an `action$` saves it. Here the app's `updateUser`
function sends the edit to the server and returns the saved user with a
server-assigned revision. The response might get lost after the server saves
the name. The app uses `mayHaveReachedServer` to recognize errors where
it needs to check whether the edit went through.

```ts
import { action$, optimistic$ } from 'octane/signals';
import { user$ } from './user-data';
import { mayHaveReachedServer, updateUser } from './api';

export const visibleUser$ = optimistic$(user$, {
	compareAuthority: (incoming, current) => incoming.revision - current.revision,
});

export const saveUser = action$('user.save', async (operation, name: string) => {
	const id = user$.get().id;
	visibleUser$.set((user) => ({ ...user, name }));
	try {
		const saved = await updateUser({ id, name, operationId: operation.id });
		operation.adopt(saved);
	} catch (error) {
		if (mayHaveReachedServer(error)) return operation.uncertain();
		throw error;
	}
});
```

Once the user data is ready, call `saveUser(name)` from the event handler.
A component that reads `visibleUser$.get().name` shows the name the person
entered while the save is in progress. When the server confirms the edit,
the saved value takes its place. If two saves finish out of order, comparing
their revisions keeps the newer result.

A definite failure removes the tentative edit. If the outcome is uncertain,
check with the server. Once you know what happened, call
`operation.adopt(value)` with the confirmed value or `operation.reject()`
to drop the edit.

<h2 id="transitions">Keep committed UI during a transition</h2>

When someone switches profiles, you can leave the current card on screen
until the next one is ready. In the client event handler, wrap the change
of ID in `startTransition`. Urgent edits can still update the page while
the new profile loads. This works during hydration, too, when the current
card came from the server.

```ts
import { startTransition } from 'octane';
import { selectedId$ } from './user-data';

export function showNextUser() {
	startTransition(() => selectedId$.set(2));
}
```

<h2 id="server-rendering">Server rendering and hydration</h2>

In a standard Octane fullstack app, the host streams the initial HTML to
the browser and sends query results as they arrive. A result can reach the
page before the code for its component does. When the component is ready
to hydrate, that result is there for it to use.

<h3 id="streaming-example">Show the page first, then its data</h3>

To try this in a [fullstack app](/docs/quick-start), put the following chat
page in `src/Page.tsrx`. The short delays stand in for database calls. The
title and the messages each have their own pending boundary, so you can
see the room's name while you're waiting for the messages.

```tsrx
// src/Page.tsrx
module server {
	export async function loadTitle() {
		await new Promise((resolve) => setTimeout(resolve, 200));
		return 'Team chat';
	}

	export async function* loadMessages() {
		await new Promise((resolve) => setTimeout(resolve, 500));
		yield [{ id: 1, text: 'Hello!' }];

		await new Promise((resolve) => setTimeout(resolve, 500));
		yield [
			{ id: 1, text: 'Hello!' },
			{ id: 2, text: 'The next message is here.' },
		];
	}
}

import { loadTitle, loadMessages } from 'server';
import { derived$, query$, signal$ } from 'octane/signals';

const title$ = query$(
	() => 'team-chat',
	() => loadTitle(),
);
const messages$ = query$(
	() => 'team-chat',
	() => loadMessages(),
	{ kind: 'stream' },
);
const draft$ = signal$('');
const draftLength$ = derived$(() => draft$.get().length);

export default function Page() @{
	<main>
		@try {
			<h1>{title$.get() as string}</h1>
		} @pending {
			<h1>Opening chat…</h1>
		} @catch {
			<h1>Could not load the title.</h1>
		}

		@try {
			<ul>
				@for (const message of messages$.get(); key message.id) {
					<li>{message.text as string}</li>
				}
			</ul>
		} @pending {
			<p>Loading messages…</p>
		} @catch {
			<p role="alert">Could not load messages.</p>
		}

		<label>
			Message
			<textarea value={draft$} />
		</label>
		<p>{String(draftLength$.get())} characters</p>
	</main>
}
```

Register the page in `octane.config.ts` so you can open it at `/`.

```ts
import { defineConfig, RenderRoute } from '@octanejs/vite-plugin';

export default defineConfig({
	router: {
		routes: [new RenderRoute({ path: '/', entry: '/src/Page.tsrx' })],
	},
});
```

<h3 id="early-input">Keep input typed before hydration</h3>

The textarea is already on the page, so someone can start typing before
the component loads. The `value={draft$}` binding connects it to a writable
signal. Octane's early capture script records those first edits, even if
someone types a message and then clears the field. Once the signal engine
and the view are active, the character count catches up with the draft.

<h3 id="streaming-performance">What reaches the browser</h3>

The first HTML to arrive has the two placeholders and the textarea. As
each query gets its first result, the server sends HTML for that boundary.
If the result matches the browser's query, the browser can reuse it and
save a second request for the same initial data.

Later lists of messages arrive as data. A view that's already active shows
them as they arrive. A deferred view keeps showing the server's HTML until
it becomes active. Each yield replaces the whole list, which is why the
second yield includes the first message again.

<h3 id="server-state-ownership">Keep server state separate for each request</h3>

If you're writing your own host with `createScope`, create a fresh scope
for every server request. The renderer and the browser need the same seed
so they agree on the values that produced the HTML. Here a compiled module
declares `route$` with `signal$('home')`. The request sets the route to
`thread` and takes a snapshot before rendering.

```ts
import { earlySignalBootstrapScript, renderToString } from 'octane/server';
import { createScope, runWithSignalOwner } from 'octane/signals';
import { App, route$ } from './view.tsrx';

export function renderPage() {
	const request = createScope({ scopeKey: 'octane:document' });
	try {
		runWithSignalOwner(request, () => route$.set('thread'));
		const initialDocumentSignals = request.serialize();
		const { html } = renderToString(
			App,
			{},
			{
				signalOwner: request,
				initialDocumentSignals,
				earlySignalBootstrap: 'external',
			},
		);
		return { earlyScript: earlySignalBootstrapScript(), html, initialDocumentSignals };
	} finally {
		request.dispose();
	}
}
```

In the response, place `earlyScript` before the rendered HTML. Include
`initialDocumentSignals` once, escaping the JSON for the HTML or script
context where you put it.

On the client, pass `hydratePage` the container with the rendered HTML,
the build and document IDs, and the original seed. Inside `hydratePage`,
initialize the document before importing any component that reads its
signals.

```ts
import { hydrateRoot } from 'octane';
import { bootstrapStreamedSignalResults } from 'octane/hydration/streamed-signals';
import type { ScopeSeed } from 'octane/signals';

export async function hydratePage(
	container: HTMLElement,
	buildId: string,
	documentId: string,
	initialDocumentSignals: ScopeSeed,
) {
	const page = bootstrapStreamedSignalResults({
		buildId,
		documentId,
		initialSignals: { version: 1, scopes: [initialDocumentSignals] },
	});
	try {
		const { App } = await import('./view.tsrx');
		const root = hydrateRoot(
			container,
			App,
			{},
			{
				signalOwner: page.signalOwner,
				initialDocumentSignals,
			},
		);
		return { root, page };
	} catch (error) {
		page.dispose();
		throw error;
	}
}
```

The seed gives the browser the values that go with the HTML it's adopting.
A live value may already be newer by then, especially if someone edited
a field before hydration. That newer value survives. Call `root.unmount()`
when you're finished with the root and `page.dispose()` when you're
finished with the document.

<h2 id="streamed-adoption">Adopt streamed results before hydration</h2>

In a custom host, you can connect a writable signal directly to a textarea
that's already on the page, without hydrating a component. On the server,
render `<textarea id="draft" value={draft$} />` using the same compiled
`draft$` exported by `./draft-state`. Include the early capture script
before the textarea. In this example the editor initializes signals once
for the whole document, using the original signal manifest in full.

```ts
import { bindSignalControl } from 'octane/signals';
import {
	bootstrapStreamedSignalResults,
	type NativeSignalManifest,
} from 'octane/hydration/streamed-signals';

export async function attachEditor(bootstrap: {
	buildId: string;
	documentId: string;
	initialSignals: Extract<NativeSignalManifest, { version: 1 }>;
}) {
	const page = bootstrapStreamedSignalResults(bootstrap);
	try {
		const { draft$ } = await import('./draft-state');
		const textarea = document.querySelector<HTMLTextAreaElement>('#draft');
		if (!textarea) throw new Error('Expected the server-rendered draft textarea');
		const stop = bindSignalControl(textarea, 'value', draft$);
		return {
			signalOwner: page.signalOwner,
			releaseControl: stop, // Before transferring this node to an island.
			dispose() {
				// Only when the document owner ends.
				stop();
				page.dispose();
			},
		};
	} catch (error) {
		page.dispose();
		throw error;
	}
}
```

If a component takes over the textarea later, call `releaseControl()`
before handing it the node. Call `dispose()` when the document ends. If
your host also needs to place streamed HTML on the page, see the
[custom SSR host setup](https://github.com/octanejs/octane/blob/main/docs/ssr.md#connect-signals-in-a-custom-ssr-host).

<h2 id="reference">Application API reference</h2>

Most of these APIs come from `octane/signals`. For the component hook
`useSignal$`, import from `octane/signals/client`. When Octane compiles
your component for server rendering, it picks the server implementation
of `useSignal$` for you. The React bindings live in `octane/signals/react`.

| Export                                                    | When to use it                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `signal$`, `useSignal$`                                   | Create writable state and update it with `.set(valueOrUpdater)`. A `signal$` can belong to a module or a component. If you pass it a function as the initial value, it stores the function itself. The `useSignal$` hook calls a function initializer once for its hook slot.    |
| `derived$`                                                | Calculate a read-only value from other signals, either inside a component or at module level. In an async calculation, `await read(handle$)` tracks a dependency even after an earlier `await`.                                                                                  |
| `query$`, `skip`                                          | Load data for a key you select, or return `skip` from the selector to leave the query idle. Call `.refetch()` to keep a ready value on screen during a refresh, or `.reset()` to show pending UI.                                                                                |
| `createScope`                                             | Keep state for as long as a cart or account session is open. Use `scope.signal$` for keyed signals and `scope.derived$` for synchronous calculations. Work with them using `scope.effect`, `scope.batch`, and `scope.transaction`. Call `scope.dispose()` when the session ends. |
| `query`, `createResource`                                 | Use `query` to define a reusable request. Calling the returned function with an argument describes what to load. In a scope you manage, `createResource` selects the request, starts the load, and gives you a handle to read the result.                                        |
| `optimistic$`, `action$`, `isActionUncertain`             | Show an edit to a ready value with `optimistic$` while you save it. Each save through `action$` gets its own operation. Check a receipt or error with `isActionUncertain` to find out whether you need to confirm the outcome with the server.                                   |
| `createFamily`                                            | Look up a keyless signal by a key such as a row ID. As rows come and go, `.delete(key)` or the `idle` option lets you evict members so the scope can release them.                                                                                                               |
| `isSignalHandle`, `isWritableSignal`                      | Check whether an unknown value is a handle you can read, or one you can also write to with `.set()`.                                                                                                                                                                             |
| `SignalScopeProvider`, `useSignalScope`, `useSignalValue` | Use these bindings from `octane/signals/react` to share a scope with React components and read a handle's value as they render.                                                                                                                                                  |

On any handle, `.get()` reads the current value. To keep showing the last
successful result, use `.latest(fallback)`. If you need to know whether a
request is pending or has failed, check `.snapshot()`. The
[signals reference](https://github.com/octanejs/octane/blob/main/docs/signals.md)
goes into more detail about ownership, retries, and hydration.
