# octane/data reference

`octane/data` is Octane's data layer for data the server owns. This page is the
reference: entry points, the store's guarantees, the wire protocol, and the
lifetimes of feeds, persistence and the cross-tab owner. For a guided
introduction with examples in `.tsrx` and React, read the
[Data guide](https://octanejs.dev/docs/data). The source in
`packages/octane/src/data/` is the specification; its module comments state
each invariant listed here.

## Entry points

| Entry | Exports | Runs |
| --- | --- | --- |
| `octane/data` | `read`, `write`, `view`, `entity`, `feed`, `DataError`; `createDataStore`, `DataUncertainError`, `DataRetiredError`; `httpTransport`, `serverTransport`, `serverListener`, `webSocketListener`, `pubSubListener`; `listen`, `receive`, `pages`; `indexedDBStorage`, `memoryStorage`, `autoBudget`; `createDataOwner`, `createReplica`, `sharedOwner`, `serveDataOwner`, `contractIdentity` | Browser, server, workers. Imports no renderer and no compiler. |
| `octane/data/server` | `createDataHandler` | Server only. |
| `octane/data/manifest` | `contracts`, `writes`, `identity` | Generated by the Vite and Rspack plugins from the `*.data.ts` modules; importing the placeholder without one throws. |
| `octane/data/octane` | `DataProvider`, `useDataStore`, `useRead`, `usePages`, `useForm`, `useFeed` | Octane components. The server compiler retargets it to `octane/data/octane/server`. |
| `octane/data/react` | The same names, over React's hooks | React 19 components. Marked `'use client'`. |

In the browser, the default store is a replica of the app's data worker:
`createReplica(sharedOwner(account), { transport, contracts, ... })`, with a
worker module that calls `serveDataOwner({ transport, contracts, listen?,
persist? })`, built through the plugins' `dataWorker` option (see
[Cross-tab owner](#cross-tab-owner)). The worker makes the requests,
validates read replies and holds feed connections and the cache, off the
main thread. `createDataStore` is the store for the server, tests, scripts
and pages built without a data worker; a replica becomes one when it cannot
reach a worker.

Both bindings read snapshots through `useSyncExternalStore`, so a store given to
an Octane tree and a React tree (for example across `ReactCompat` or
`OctaneCompat`) shows the same values, pending edits and rollbacks in both.

## Contracts

A contract is an inert description. Declaring or importing one does no I/O.
Schemas are [Standard Schema](https://standardschema.dev) validators. A
synchronous validator validates synchronously, so a write can show its edit in
the same task as the event that caused it.

| Contract | Options | Notes |
| --- | --- | --- |
| `read` | `name`, `input?`, `output`, `entities?`, `tags?`, `fresh = 0`, `keep = 300000`, `expire = Infinity`, `persist = true`, `cancel = false`, `version = ''` | Times are milliseconds; a `keep` of 2³¹ ms or more (such as `Infinity`) keeps the value for the session. `entities(output)` returns `Entity.from(...)` selections. `tags` is a list, or `tags(input)` for each input. `cancel` aborts a load when its last fetching subscriber leaves and nothing else needs the result. |
| `write` | `name`, `input`, `output?`, one of `creates`/`patches`/`removes`, `draft?`, `serverId?`, `record?`, `form?`, `invalidates?` | `draft(input, id)` defaults to the input plus the new ID. `record(output)` locates the saved record so views take it without reloading. `invalidates` is a list, or `invalidates(input)` from the validated input. |
| `entity` | `name`, `schema`, `key = 'id'` | `id(value)` is `String(value[key])`. `one` and `list` are output schemas of one record and of a list, validated by `schema`: a read whose `output` is one of them selects the entity without `entities`, and a `creates` or `patches` write to the entity whose `output` is `one` takes its reply as the saved record without `record`. An output of `schema` itself selects nothing. |
| `view` | `name`, `of`, `order`, `where?`, `with?`, `input?`, `limit = 20`, `max = 500`, plus the read options | A read whose input is `{ ...params, offset, limit }` and whose value is that window's rows. `view.view.where` and `view.view.compare` are exposed for handlers. `with: { name: [Entity, key] }` joins each row to the record its `key` points at. |
| `feed` | `name`, `params?`, `event`, `changes(event, params)`, `covers` | `changes` returns `{ put, value }`, `{ remove, id }`, `{ read, input?, value }` or `{ invalidates }`, or an array of them. |

Contracts declared in `*.data.ts` modules can be checked by the build: the
Vite and Rspack plugins and `octane analyze` report a used contract no handler
serves, one served twice, duplicate names, and unused contracts, once the app
imports `octane/data/manifest`. The rules and codes are in
[Strong compiler checks](strong-compiler-checks.md#data-contracts).

`view` ordering compares values as JavaScript's `<` does (dates by time,
`null`/`undefined` first), then by the entity key's own value (so integer keys
sort numerically). A handler must serve the same order: a window whose rows
are out of it fails validation, in the handler and in the store, with
`invalid` and an issue naming the view. An order only the server can run,
such as a language collation, belongs in a read with cursor `pages`.

Tags computed from an input scope invalidation to that input. A read
computes its tags once per input, as `store.read` was given it; a view's
input also carries any `offset` and `limit`. A write computes its
`invalidates` from its validated input when it is sent, to pick the reads
refreshed in its reply, and again when it settles. Saved values keep the
tags computed for them, so a later invalidation still reaches them after a
restart.

```ts
const project = read({
	name: 'project',
	input: ProjectId,
	output: Project,
	tags: (id) => [`project:${id}`],
});
const rename = write({
	name: 'renameProject',
	input: Rename,
	invalidates: ({ id }) => [`project:${id}`],
});
```

A view `with` relations has rows of the record plus, under each relation's
name, the record its key points at. The handler returns each row with those
records, or `null` or nothing where there is none; each part is validated by
its own entity's schema. `where` and `order` see the view's own record only.

## Store guarantees

`createDataStore({ transport, seed?, seedAge?, form?, persist?, listen?, feeds? })`.

- Describing or snapshotting a read does no network work. By default,
  subscribing, prefetching and refreshing can start a load. Readers of one
  entry share it. Inputs are compared by value.
- `handle.subscribe(notify, { fetch: false })` observes the same entry while
  pausing automatic fetches for that subscriber. The store can restore a saved
  value and deliver updates from other subscribers, writes, feeds, `publish()`,
  `prefetch()` and `refresh()`. Expiry and account checks still apply.
  Resubscribe with `fetch: true` or omit the option to resume normal loading.
  In either binding, use `useRead(handle, { suspend: false, fetch: canFetch })`
  and change `canFetch` on render.
- `getSnapshot()` is stable between changes. A snapshot is
  `{ status, value, error, refreshing, stale, more, preview }`; `value` is the
  newest confirmed value with pending edits applied, or, while `preview` is
  true, a provisional value of the load in flight.
- A transport may send previews of a read (not of a view) while its reply is
  pending. Each is validated by the read's `output`; an invalid one is
  skipped. A read with no confirmed value to show is `ready` with the newest
  preview, in the order they were sent whatever order they validate in. The
  reply replaces it in one snapshot change; a failure removes it, and the read
  stays failed until it is refreshed. A read with a confirmed value keeps
  showing that value. A preview takes no pending edit, shares no record, and
  is never saved or dehydrated. Previews of a superseded load are ignored.
- A read with `cancel: true` aborts its load when its last fetching subscriber
  leaves or pauses, unless a `prefetch()` or `refresh()` joined that load,
  which then runs to its end. The confirmed value stays available.
- A write is sent once. A transport rejection after dispatch leaves it
  uncertain (`DataUncertainError`), with its edit shown, until
  `settle(operationId, confirmed, value?)` names the outcome.
- Only a reply for an entry's current attempt, in a store that has not been
  retired, changes confirmed state.
- Writes to a record whose create is unconfirmed wait for it. They are refused
  unsent if it is refused, and carry the server's ID if `serverId` assigned one.
- Every value one reply carries is adopted before any reader is notified.
- A changed record reaches the reads that select it, the lists a created
  record joins, and the views of its entity. An optimistic edit, a settled
  write or a feed event does work for those reads only, so its cost does not
  grow with the reads the store holds. A read it does not reach keeps its
  snapshot, including an age-based `stale` flag, until its own next change.
- Every optimistic edit is an absolute patch, an insert by ID or a delete by
  ID, so it replays over any newer value without counting twice.
- A record is whole: a newer copy replaces an older one entirely, never field
  by field, and only when its load started later. A read that returns part
  of a record's fields must not select its entity.
- A view's records are shared: one table per entity holds the newest confirmed
  copy of each record any view loaded, and every view of the entity is
  evaluated over it with outstanding edits applied. The store loads a margin
  beyond the visible window.
- A view's related records are shared records of their own entities. A row
  shows each with outstanding edits applied, and is the same object until its
  record or one of its related records changes. A change to a related record
  reaches the views holding a row that points at it, and is saved with them.
  A view reloads once when a shown row points at a record its last load did
  not cover and the store does not hold, after any edit to that row has
  settled. A related record is kept while a view holds a row that points at
  it.
- A seed is adopted when its read is first asked for, and keeps its age
  (`seedAge` adds time spent in a cache).
- A value no reader has shown yet, from a seed or a `prefetch`, is not
  reloaded for its age by its first reader or by another `prefetch`, so a
  route that prefetches hydrates without loading, and a link prefetched on
  hover loads once. Once shown, a value older than `fresh` reloads.
- `dispose()` ends one store locally, clears its memory immediately, flushes confirmed saves already queued after persistence has initialized, and preserves durable storage for another window or restart. A store disposed before initialization cancels its pending saves. A later `retire()` can still erase the account cache.
- `retire()` clears memory at once, ignores late replies, and resolves once
  persistent storage is cleared. Later writes, invalidations and settlements
  throw `DataRetiredError`; later reads stay pending without loading.
- `dehydrate()` returns text safe inside `<script type="application/json">`.
  Call it on a server store after the render completes, then retire the store.

## Pages

`pages(store, view, params?, size?)` reads a view `size` rows at a time.
`pages(store, read, input, { rows, next })` reads a list whose server returns
a page and a cursor: `rows(page)` is a page's rows and `next(page, input)` the
input of the page after it, or `null`/`undefined` at the end. Both return one
handle per store for equal arguments, with `getSnapshot`, `subscribe`,
`loadMore` and `refresh`.

- A snapshot is a read snapshot of the joined rows plus `loadingMore` and
  `loadMore`. `value` is the same array until a row changes. The page being
  added shows its preview among the rows, with `preview` true.
- `loadMore()` adds the next page once the last is confirmed. While that page
  loads, it joins the load. While a page has failed, it loads that page
  again, at the same input.
- A cursor list adds a page only at an input no page of it has read, so a
  missing or repeated cursor ends it. An empty page with a new cursor goes on.
- When a confirmed page of a cursor list names another next page than the one
  loaded, because it was refreshed, invalidated or reloaded, the pages that
  now follow load out of sight. The list shows what it last showed, with
  `refreshing` true, and replaces its rows once every replacement is
  confirmed. If one fails, the list stays, with `error` set, and `loadMore()`
  loads that page again. `refresh()` reads the chain again from its first
  page this way, for as many pages as the list showed.
- A view's `refresh()` reloads every page at once.

## Wire protocol

Transports and handlers exchange devalue-encoded messages, so dates, maps and
sets survive.

```ts
interface DataRequest {
	kind: 'read' | 'write' | 'position';
	name: string;
	input: unknown;
	operationId?: string; // writes
	refresh?: Array<{ name: string; input: unknown }>; // reads on screen a write asks back
}

type DataReply =
	| { ok: true; value: unknown; refreshed?: Array<{ name: string; input: unknown; value: unknown }> }
	| { ok: false; code: string; data?: unknown; issues?: SchemaIssue[] };

type Transport = (
	request: DataRequest,
	signal: AbortSignal,
	preview?: (value: unknown) => void,
) => Promise<DataReply>;
```

A resolved reply is definitive. A rejection means the outcome is unknown. A
read's transport may call `preview` with whole provisional values before it
resolves; `httpTransport` and `serverTransport` send none. `signal` aborts
when the store no longer wants the request: it was superseded, the store
retired, or a `cancel` read lost its last subscriber. A
write may ask for at most eight reads back; the rest reload on their own.
`httpTransport` rejects any response that is not a reply, such as a proxy's
error page.

Feeds use a `Listener`, `(request: { name, params, cursor }, signal) =>
AsyncIterable<FeedFrame>`, where a frame is `{ event?, id?, cursor?, gap? }`.
An empty frame says the connection is open.

## Handler

`createDataHandler(options, define)` from `octane/data/server`:

| Option | Meaning |
| --- | --- |
| `context(request, caller?)` | Authenticates a request and returns what handlers receive. `caller.viewer` and `caller.platform` come from server-function or middleware context. |
| `allowedOrigins` | Origins other than the request's own that may call. Requests with no `Origin` are allowed. |
| `secret` | Signs form tokens. Required for `forms()`. |
| `grant(context)` | The account a request acts for; a form signed for one account is refused for another. |

`define(handle, defineHandler)` returns `handle(contract, run)` entries; names
must be unique. `defineHandler(Module, { key: run })` takes a module namespace
(`import * as Module from './x.data.ts'`) and returns one entry per read,
view, write or feed it exports. Its type requires exactly one `run` per
contract export, typed as `handle` types it; a missing or extra key is a type
error, a missing one at runtime throws, and other exports are ignored.
`Implementation<C, T>` is the type of `run` for contract `T`.
A `read`, `view`, `write` or `feed` declared with its `run` as a second argument,
`read(options, run)`, is served by it: `defineHandler(Module)` needs no key
for it and takes no object when every contract has one. Its `call` type names
what `run` needs from the context (`Served<Context>`), and `defineHandler`
accepts the module only for a context that provides it. The Vite and Rspack
plugins drop each `run`, and the imports and module-level `const`s only those
functions used, from the client build of a `*.data.ts` module. A contract
module may import types from any module. `run(input, call)` receives validated input and `call`: the context
plus `request`, `signal`, `operationId` and `read(contract, input)`. A view's
`run` receives `{ ...params, offset, limit }`. A feed's `run` is an async
iterable of frames and receives `call.cursor`. Throw `DataError(code, data?)`
to refuse.

The returned `DataServer` is a `(Request) => Promise<Response>` function with:

- `transport(request)`: an in-process transport for a server render of
  `request`.
- `serve(request, call)`: answers one request sent by `serverTransport`
  through a `module server` function.
- `listen(request, call)`: answers one feed connection sent by
  `serverListener`. Connections end after 25 seconds; the store reconnects
  from its cursor.
- `accept(socket, request, caller?)`: serves `webSocketListener` sockets with
  no time limit. Cross-origin sockets are refused.
- `forms(request, caller?)`: signs a page's forms and runs a native form POST.
  Returns `{ response, status, form }`: send `response` (a 303) when set,
  otherwise render with `status` and pass `form` to the page store.

## Forms

A write with `form` accepts native POSTs. Field codecs: `text`, `secret`
(never echoed back after a refusal), `number`, `boolean` (`"true"`/`"false"`),
`checkbox` (present or absent). Every declared field except a checkbox must
appear exactly once, and undeclared fields are refused. Field names starting
with `$` are reserved for the hidden fields that name the write, the form key,
the signed token and the operation.

`store.form(write, key?)` and `useForm` expose `pending`, `values`, `issues`
(first message per field; whole-input under `''`), `error` (a refusal code or
`'uncertain'`), `hidden(values?)` and `submit(eventOrFormData)`. The binding
view adds `attrs`, `{ method: 'post', onSubmit }`, which submits through the
store once hydrated. Only the newest submission's outcome is shown.

### Recovering a submitted form

A keyed form stays in the store while its submission is pending or its
refusal is shown, even when nothing renders it. A dialog can close as soon as
it submits, and a refusal can reopen it with what was submitted.

- A definitive refusal (`DataError`) removes the optimistic edit and rejects
  `submit()`. The form shows the refusal's `error` code, its `issues`, and the
  submitted `values` as text, with `secret` fields left out. The next
  submission of the form replaces them.
- A transport failure after dispatch is uncertain: the edit stays, `submit()`
  rejects with `DataUncertainError`, and the form shows `error: 'uncertain'`
  with its `values`. Only the rejection carries the `operationId`.
- The form keeps showing `'uncertain'` after `settle` decides the write, until
  it is submitted again. After a confirmed `settle`, the app stops showing the
  form's error itself.

Which dialog is open, and what a retry looks like, belong to the app. In this
example the dialog closes on submit, the book that owns it reopens it on a
refusal, and an uncertain write is looked up before a retry is offered.

```tsx
import { useEffect, useState } from 'octane';
import { DataError, DataUncertainError } from 'octane/data';
import { useDataStore, useForm } from 'octane/data/octane';

function RenameDialog({ id, close, uncertain }) {
	const form = useForm(renameBook, id);
	return (
		<form
			{...form.attrs}
			onSubmit={(event) => {
				const saving = form.submit(event);
				close();
				saving.catch((error) => {
					if (error instanceof DataUncertainError) uncertain(error.operationId);
					// A refusal shows in the form; anything else is a bug.
					else if (!(error instanceof DataError)) throw error;
				});
			}}
		>
			{form.hidden({ id })}
			<input name="title" defaultValue={form.values.title} />
			{form.issues.title && <p>{form.issues.title}</p>}
		</form>
	);
}

function Book({ id }) {
	const store = useDataStore();
	const form = useForm(renameBook, id);
	const [open, setOpen] = useState(false);
	const [retry, setRetry] = useState(false);
	const refused = form.error !== null && form.error !== 'uncertain';
	useEffect(() => {
		if (refused) setOpen(true);
	}, [refused]);
	const uncertain = async (operationId) => {
		// The app's own lookup: did the server apply this operation?
		const applied = await renameApplied(operationId);
		store.settle(operationId, applied);
		// Not applied: offer to submit the same values again, as a new operation.
		setRetry(!applied);
	};
	return (
		<>
			<button onClick={() => setOpen(true)}>{retry ? 'Retry rename' : 'Rename'}</button>
			{open && (
				<RenameDialog id={id} close={() => setOpen(false)} uncertain={uncertain} />
			)}
		</>
	);
}
```

A store with `persist.journal` settles a journaled write's uncertain outcome
by itself after a restart; within a session, deciding it is the app's.

### Write order and dependencies

- Writes with an effect on the same record are sent one at a time, in the
  order they were submitted, so the last edit wins on the server too. Each
  shows its optimistic edit at once.
- That order is not a success dependency. A later edit to a record is still
  sent after an earlier edit to it is refused or its outcome is unknown. Only
  a record's create gates the writes after it: they wait while it is pending
  or uncertain, and are refused unsent with code `'dependency'` if it is
  refused.
- Writes to different records, and writes with no effect, are sent
  concurrently. The default HTTP transport sends one request per write.
- The order is per store. Writes another tab or another client sends are not
  ordered with them.

When a write must only happen if another succeeded, await the first:

```ts
await store.write(moveBook, { id, shelf: 'archive' });
await store.write(setDone, { id, done: true });
```

The second edit then shows only once the first is confirmed. To show both at
once and still apply them together, make them one server write whose handler
does both in one transaction; the store shows that write's own effect. A
dependency that shows every edit at once is not built in.

## Feeds

- One connection per store, feed and parameters, open while observed and
  closed when the last observer leaves or the store retires.
- Frames apply in order. Event IDs seen recently (256 per feed) apply once.
- The store resumes from the last cursor, which a persistent store saves with
  the values it covers. On a gap frame, an event that fails validation, or a
  cursorless connection returning after a live one dropped, every read in
  `covers` is marked stale.
- Failed connections retry with growing, jittered delays up to 30 seconds.
- A store with `feeds` and no `listen` (a server render's) asks each feed for
  its position before its first read; the seed carries it. A feed handler that
  can resume yields its position first when `call.cursor` is null.
- `receive(store, changes)` applies changes without validation.

## Persistence

`persist: { storage, partition, key, budget?, journal? }`.

- Values are encrypted with a key derived from `key` (at least 128 random
  bits, or an HKDF `CryptoKey` with `deriveKey` usage), and every name the
  storage sees is a keyed hash.
- Only confirmed values are saved. Values saved under another output schema
  shape or `version` are discarded unread; values that fail validation on
  restore are discarded.
- Reads and views normally restore first and fetch only if needed. Set
  `restore: 'concurrent'` on a read or view when it must start one live
  request immediately, even if storage is slow. A valid cached value can show
  while that request runs, but a late restore cannot replace its accepted live
  value. Refresh joins that initial request. If it fails, a valid cached value
  can still show alongside the error. `persist: false` disables restoration.
- Stale marks survive restarts: each tag and entity keeps when it was last
  marked.
- Saves coalesce into one storage transaction per host task.
- After each save the partition is trimmed to 90% of `budget`, expired values
  first, then least recently used; values a mounted component shows are kept.
  `autoBudget(device)` is 1 MB at ≤2 GB memory, 2 MB to 4 GB or when hidden,
  5 MB above, halved under data saver, capped at 1% of the quota.
- `journal: { writes, receipt }` saves each listed write before sending it.
  After a restart its edit shows again and `receipt({ operationId })` decides
  it; it is never resent. Undeclared or incompatible journal entries are kept
  30 days for a compatible build.
- `PersistentStorage` is `index`, `get`, `commit`, `clear`; it only receives hashed names and encrypted values. A fixed numeric budget does not query device quota hints. Independent stores sharing a partition do not coordinate logout: a trusted host must stop old writers before erasing or reusing that partition. Use an explicit shared owner when windows need coordinated account admission and one persistence writer.

## Cross-tab owner

- `createDataOwner({ transport, listen?, contracts? })` makes every request and
  holds every feed connection for its replicas; `connect(port)` serves one.
- With `contracts`, every read, write and feed the app uses (the data worker
  imports them from `octane/data/manifest`), the owner validates each read's
  reply with its output schema when its contracts' identity is the one its
  tabs share, and a tab adopts that value without validating it again. It
  leaves the reply to the tab's own validator when validation fails (the tab
  reports the issues) and when the validated value holds anything a
  structured clone would change: a class instance, a function, a symbol or a
  null-prototype object. Previews, seeds, cached values and the reads a write
  returns are validated in the tab as before.
- `createReplica(owner, { ...storeOptions, contracts })` takes an ordinary
  store's options plus `contracts`, every read, write and feed the app uses.
  It renders, evaluates views and shows its own edits in the same task. It
  carries on as a local store, with its own `transport`, `listen` and
  `persist`, when `owner` is `null`, its worker fails to load, the owner refuses its build, cannot record
  the account, or is lost and cannot be reopened.
- The owner sends each write once. Other replicas show it from the moment it is
  sent and settle it the same way. Equal reads in flight are one request,
  except a replica's reload never joins a request that may predate it. One
  upstream connection serves every replica listening to a feed with the same
  parameters.
- A read's request runs while a replica waits on it. A replica lets go when
  its store aborts the request's signal, and the owner aborts its transport's
  signal once the last replica waiting has let go. Each preview reaches every
  replica waiting on the request, and one that joins it starts from the
  newest.
- `serveDataOwner(options)` is the data worker module's entry. The `dataWorker`
  option of `octane()` from `octane/compiler/vite` or `@octanejs/vite-plugin`,
  and of `OctaneRspackPlugin`, emits it at `/_octane/data-worker.js`.
  `sharedOwner(name, url?)` returns that SharedWorker's port, named by protocol
  version and `name`. Where SharedWorker is missing or cannot start, it runs
  the same module as a dedicated `Worker` of the page, which the page's
  replicas of `name` share: the owner's requests, feeds and persistence stay
  off the page's thread, but each tab has its own owner, as each has its own
  store without one. It returns `null` where neither can start. A worker that
  fails to load makes each of its replicas a local store; a dedicated worker
  that stops answering is terminated and replaced.
- `createDataOwner({ fence: true })`, which `serveDataOwner` always sets,
  fences accounts. The origin has one account at a time, recorded in IndexedDB
  (`octane-data-account`) with a generation that increases on every sign-in
  and sign-out, durably before any replica hears of it, and announced on the
  `octane-data:account` `BroadcastChannel`. `sharedOwner(account)` opens with a
  `hello` naming the account. A different account signing in retires every
  replica of the old one: values clear, pending requests reject with
  `DataRetiredError`, feeds end, and nothing in flight reaches a replica.
- `dispose()` on a replica detaches only that window, stops its heartbeat and preserves its peers and owner persistence.
- `retire()` on a legacy-fenced replica signs its account out in every tab and repeats the
  request every 5 seconds until the owner confirms. A sign-out records only if
  its generation is still current, so it never undoes a newer sign-in.
- For trusted host account lifecycle, opt into `createDataOwner({ fence: 'explicit' })` or `serveDataOwner({ fence: 'explicit' })`. Explicit mode uses a separate account database/channel and a separate persistence partition for each durable account generation, so migration starts with a cold cache and late prior-generation commits cannot appear in a new grant. Only trusted code holding the owner object calls `activate(account)` or `activate(null)`; activation rotates the durable generation, clears the prior generation, and publishes the grant only after that cleanup succeeds. A separate old owner can still finish a previously started commit into its isolated old partition before receiving revocation; the new grant cannot restore it. For physical deletion to be complete when activation resolves, the trusted host must stop and await all old owners before activating the replacement. Replica hello/reopen only joins the active grant. Replica `retire()` and raw persistence-clear messages cannot revoke or erase peers in this mode. Never expose `activate` over an untrusted replica port; explicit mode does not itself authenticate the host, and the host must serialize its account transitions and revoke old windows. The trusted host must authenticate port/account admission and keep one live owner per grant; a fresh owner may adopt the durable grant only when replacing a stopped worker.
- A replica's reads show pending while its page is frozen. On `resume` it asks
  the owner, and shows them again only once the account is confirmed.
- A tab's `hello` carries its contract identity: each contract's kind, name,
  `version` and output schema shape. The first build served sets the owner's;
  a tab of another build is refused and carries on as a local store.
- Tabs and owners check on each other every 5 seconds; three silent intervals
  mean gone. A tab whose owner is gone fences its reads, reopens the worker,
  asks the new owner every read the old one never answered, and rejects writes
  that were in flight as uncertain, never resending them. An owner drops a
  silent tab's feed subscriptions; its writes keep going.
- While a replica is fenced, `prefetch` waits for the fence to lift, so a
  suspended reader shows the confirmed value rather than none.
- The owner protocol version (5) is part of the worker's name, so tabs on
  another protocol never share an owner.
- `createDataOwner({ persist: (account) => PersistOptions })`, which
  `serveDataOwner` passes through, makes the owner the only writer of the
  account's encrypted cache and write journal. A replica with `persist`
  forwards every persistence call to it (restore, save, journal, stale marks,
  feed cursors, clear), so tabs share one cache and one budget; only the first
  tab to recover the journal after a restart gets its entries. Signing out, or
  another account signing in, clears the cache. A replica uses its own
  `persist` only once it is a local store.
- The cache keeps a read's value from the newest request the owner made for
  it. A reply to an older request that lands later shows in the tab that asked
  for it, and is not saved over the newer value.
- A read's value crosses to a tab once. Where the owner validated it, or the
  tab's output validator returns the value it was given, the tab tells the
  owner it validated and the owner saves its own copy; the tab sends the value back only where its
  validator returned another representation, the value changed since, or an
  earlier reply to that read was still waiting to be saved. A read with
  `persist: false` is never kept by the owner. A view saves its rows as
  before.
- A durable write in flight to an owner that crashes settles by itself: once
  each tab reconnects, it looks up the receipt of every journaled write it
  shows as uncertain and keeps or rolls back the edit. The owner looks each
  receipt up once and gives every tab that asks the same answer, so tabs
  settle a write the same way. A write that is not journaled stays uncertain
  until the app settles it.
- A tab that recovers the journal leaves out the writes still in flight
  through the current owner: they belong to the tab that sent them.
- A replica hydrates from its page's seed without waiting on the owner, then
  offers each seeded read (not view) to the other tabs with its load time. A tab holding
  an older value takes it; one holding a newer value offers its own back, so
  every tab ends up showing the newest. Joining a feed connection that stands
  at another position than the seed's cursor is a gap: the replica reloads
  what the feed covers.

## Errors

| Error | Meaning |
| --- | --- |
| `DataError` | Definitive refusal. `code`; `data`; `issues` for validation (`code === 'invalid'`). |
| `DataUncertainError` | A write's outcome is unknown. `operationId` identifies it for `settle`. |
| `DataRetiredError` | The store was retired. |
