# Signal Chat renderer size investigation

This measures the unchanged production Signal Chat route. It does not remove a renderer feature or establish a safe specialized renderer. The existing application bootstrap and each independent island activator can require the same renderer; the load-triggered Metrics island uses state, effects, a timer and `@try`, so deferring only the outer shell does not keep that renderer cold.

The experiment snapshots the example once and runs three Vite production builds. `baseline` and `control` use Vite's default Oxc minifier; the third slot, named `fallback` for compatibility with the existing route browser runner, uses Vite's ordinary Terser minifier with default options. It is a minifier control, **not** a shell fallback. No unsafe minifier options, assumed-pure calls, feature exclusions, source rewrites, or application changes are used. All three builds retain the five independent island entries, their server manifests and the stylesheet.

The builds use hidden source maps for attribution. The historical temporary evidence directory was named `octane-runtime-size-pPlneP`; it is not published with this repository and may have been removed by the OS. Its source snapshot SHA-256 is `5dd762d9b50a9f933d6a90ede20e52dd0e6d18a603f79f27b8237c514c1d5d0d`, selected toolchain SHA-256 is `aec368653d232214a9aa510bc4330bc1effb73a57fdc404fae4a66993f2dab9d`, and experiment-script SHA-256 is `945b5a423b941f50ac0c992e2b9c84ab9378924b9fcf8dfb0a8a10201381f5bb`. These hashes do not cover every installed dependency or OS component. The instrumented output was not compared with a no-map build against this same runtime checkpoint.

These are sums of independently compressed physical files across the Vite manifest graph, including every emitted client JavaScript file. The static-entry closure is not the whole browser startup: dynamically loaded islands and streamed-signal support also request files. Terser increased complete reachable gzip by 2,596 bytes (about 1.7%) in this build; it is not a size improvement. Offline file compression is separate from bytes transferred by the server and reported by Chromium.

In one local Chromium 149.0.7827.55 sample for each profile and scenario, the medium interaction route requested 14 JavaScript files totaling 148,943 encoded body bytes for both default builds and 151,513 for Terser. The medium eager route requested 17 files totaling 154,292 and 156,928 bytes respectively. These are browser-reported response bodies; the server gzip-compressed most JavaScript. The browser checks also exercised both workload profiles, delayed activation, failure and retry, early draft/focus/selection and DOM identity through adoption, a stream that continued after activation, and a form navigation. One RPC cancellation (`net::ERR_ABORTED`) was recorded during each successful send and retry for every variant; the run is not evidence that every request succeeded. These checks support the exercised behaviors only and make no latency or full-equivalence claim.

## Where the code is

The default build's shared renderer chunk is 302,165 raw bytes, or 92,513 bytes offline gzip-9. Rolldown reports 96 rendered exports from `runtime.ts` in that chunk, including `hydrateRoot`, the independent activator, `tryBlock`, state and layout-effect support. `ViewTransition`, `Activity`, `createPortal` and `useTransition` are not among its rendered exports, while `startTransition` is. The absence of an export does not prove that all implementation paths related to it vanished, and a retained export or source span does not prove that it can be safely removed.

Approximate source-map attribution accounts for 281,799 generated bytes mapped to `runtime.ts`, 189,558 mapped to other sources, and 11,737 unmapped bytes across all client chunks. The largest navigation bands in `runtime.ts` include hydration helpers, host properties and events (46,012 mapped raw bytes); suspense/activity-area code (39,871); host/descriptor reconciliation (35,243); and scheduler, transition and journal-area code (25,373). Those bands contain shared machinery and are **not** independent removable feature totals. Source maps may be sparse or attribute inlined code to a shared location; unmapped bytes include Vite-generated chunks with no source map. Gzip cannot be assigned independently to these overlapping regions.

Current automatic metadata cannot prove that any of these clusters can be removed safely. The scheduler, adoption and recovery paths participate in effects, events, streamed signals and independent roots. A renderer alias would need a whole-graph capability proof and a fallback for dynamic paths, hydration mismatch, remount and updates, while preserving shared owner state and side effects. Its fallback and any newly duplicated chunks must be included in the result. The source-map report identifies where to investigate; it is not proof of a possible saving.

## Earlier checkpoint

Before the framed-root recovery fix, the same experiment produced 483,092 raw / 154,796 gzip-9 reachable JS bytes for each default build and 494,023 raw / 157,391 gzip-9 for Terser. Its medium interaction route requested 148,941 and 151,511 browser-reported encoded JS bytes respectively. The earlier instrumented default had the same raw graph size as the earlier non-map production build, with at most a two-byte offline gzip difference across build identities; that comparison does not establish parity for the later checkpoint. The earlier temporary evidence directory was named `octane-runtime-size-YicK4X` and is not published here. Its selected toolchain SHA-256 was `eb99c7ff8d606f929de4a9c78684b0b975dc91c8ed985f7ab434beb722c4df7f`.

## Reproduce

From this worktree with the existing lockfile-matched dependencies:

```sh
node benchmarks/streamed-shell-prototype/runtime-size/run.mjs
node benchmarks/streamed-shell-prototype/runtime-size/attribute.mjs /absolute/output/from/run
PLAYWRIGHT_EXECUTABLE_PATH='/absolute/path/to/authorized/chromium' \
  node benchmarks/streamed-shell-prototype/signal-chat-route/browser.mjs \
  --build-dir=/absolute/output/from/run --samples=1
```

`run.mjs` snapshots the application and hashes the selected framework/toolchain and experiment scripts before and after building. `attribute.mjs` verifies the inputs and emitted artifacts, including the captured module metadata, before mapping generated bytes. The route runner verifies build provenance and emitted files before exercising separate production servers. Browser samples are functional and payload observations, not latency measurements. The generated entry's `fallback` label refers to the Terser control here.
