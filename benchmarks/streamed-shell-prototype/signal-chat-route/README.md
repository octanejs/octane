# Signal Chat route comparison

This measures the copied, production-built Signal Chat application, including its generated app bootstrap, real Node SSR handler, five independent hydration entries and stylesheet. The three builds use the same frozen source: `baseline`, a repeated `control`, and `fallback`, which runs the experimental automatic-shell plugin on the actual `App.tsrx`. The plugin currently rejects this route and leaves the ordinary compiler in control. This compares the cost of rejection with repeated build variation; it is not a successful shell elimination.

From the worktree root, with the installed dependencies already present:

```sh
node benchmarks/streamed-shell-prototype/signal-chat-route/prepare.mjs
PLAYWRIGHT_EXECUTABLE_PATH='/absolute/path/to/authorized/chromium' \
  node benchmarks/streamed-shell-prototype/signal-chat-route/browser.mjs --build-dir=/absolute/path/printed/by/prepare --samples=2
```

`prepare.mjs` prints and creates a fresh temporary output directory. It snapshots the whole example, builds each variant in a private copy, captures Vite's client manifest and records source, selected framework/benchmark source, lockfile, generated server and client artifact hashes. The browser runner verifies those hashes before use; the selected-source provenance is not a complete record of installed dependencies or the operating system. `--smoke` runs one medium baseline case into a separate report for harness development. Run the full comparison serially when collecting observations.

The graph report counts every emitted client JS file reachable from the generated Vite entry. It separates static entry dependencies, dynamic reachable chunks and CSS; gzip-9 is an offline sum per file, not traffic. Five independent activation entries must remain present. The actual browser observations use fresh Chromium contexts, no service worker, and an ephemeral loopback server using the generated production handler and the framework's Node static adapter. They separately record each requested resource, Chromium-reported encoded response body and header size, content encoding, browser resource timing and document/stream body sizes. The server also counts completed response bodies and headers, including the browser-generated missing favicon request that Playwright does not expose as a page request. The small HTTP wrapper adds measurement overhead. The actual static adapter applies gzip to eligible CSS and JavaScript; the streamed HTML response is identity-encoded. Chromium page-request sizes and Node response payload/header counts are separate observations and can differ with HTTP transfer framing; neither includes physical-network overhead. Timings are not compared as production latency. These are not production network or physical-device measurements. Timing observations from a few localhost samples are noisy and are not a benchmark conclusion.

Both 20-turn/10-history-row and 200-turn/60-history-row profiles run with the same bounded four-yield delays, across the interaction route, eager route, delayed root hydration and a failure-before-first-answer case. The runner checks generated content counts and server producer completion. Additional browser checks block external scripts until the browser receives the complete streamed document, verify pre-activation revision, preserve an early textarea value, node identity, focus and selection through adoption, activate independent panels and send a new prompt. A separate slow-stream case activates the conversation before completion and observes a later revision and preserved nodes; others check failure retry and the native configuration form's distinct turn/history counts. Full form navigation is not a same-root remount or BFCache test. Document streams and separate trace requests are real HTTP traffic. Browser startup accounting uses a no-interaction idle checkpoint, and does not count later user-triggered chunks as startup; all reachable dynamic chunks are still present in the graph report. Server-side identity-encoded document capture records actual body/chunk observations and offline gzip; stream-script bytes count matched inline stream-carrier elements, not a protocol-level frame size.

This experiment does not establish a valid client surrogate for the route. Normal mount/remount and hydration mismatch recovery need a real fallback; native adoption can retry via normal rendering, so a hydration-only surrogate is not safe merely because the first entry was hydrating. A wrapper-only synthetic size is not the app's potential saving.
